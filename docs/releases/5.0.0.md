# AE Development Rules 5.0.0

Дата релиза: **2026-10-02**. Версия: [VERSION](../../VERSION). Лицензия: [MIT](../../LICENSE). [GitHub Release](https://github.com/ios3kov/AE-Development-Rules/releases/tag/v5.0.0) содержит точный commit, архивы и Evidence публикации.

## Назначение и изменения

Свод правил для ИИ, который разрабатывает AE-продукт по подтверждённой пользовательской цели. Инженерные требования также применимы к разработчикам. Релиз включает canonical rules, профили технологий, reusable scripts, schemas и templates.

Это **major**-версия по Engineering §34: новые обязательные правила приоритета и доверия, восстановления состояния задачи, сохранения границ разрешений и проверки точных источников новых/изменяемых host API меняют процесс принятия решений.

- Smart Entry различает существующий контракт и его покрытие текущего scope, сохраняет подтверждённые решения и осознанно принятый baseline.
- Внешние документы и ответы инструментов не предоставляют разрешений; продолжение задачи восстанавливает актуальное состояние и пользовательские границы.
- Неизвестное критическое поведение блокирует зависимое проектирование. Запись предположения сама по себе не устраняет зависимость; независимая разрешённая работа продолжается.
- Повторная неудачная попытка требует нового основания или ограниченного обоснованного retry. Значимые требования связываются с задачей, acceptance и проверкой/Evidence в существующих документах.
- Validation разделяет обязательные prerequisites до передачи, безопасный пользовательский вопрос и финальную Release acceptance. Недоступный обязательный prerequisite и известный FAIL проверяемого сценария блокируют передачу.
- Выбор правил включает диагностику bugfix, API sources и применимые минимальные Light-требования. Подпись PKG-контейнера и проверка исполняемого payload различаются.
- Инструменты отвергают некорректные диапазоны, разреженные component/pixel arrays, неконечные производные render metrics и пустые N/A explanations. Stable RMSE сохраняет конечные представимые результаты.
- Добавлены 20 сценариев поведения ИИ с 21 контролируемым starting state, подготовкой fixture и частичной проверкой файловых изменений.

Подробности и сохранённые исходные Evidence: [CHANGELOG](../../CHANGELOG.md), [A01–A13 / R01–R06](../AUDIT_REMEDIATION.md), [AI update](../AI_PROTOCOL_UPDATE.md), [F01–F12](../AI_PROTOCOL_REMEDIATION.md).

## Совместимость и переход

1. Проверить применимые изменения, сохранить прежнюю версию/SHA своего проекта и зафиксировать решение о переходе. Существующий compliant project может потребовать новых process records; upgrade не происходит автоматически.
2. Для значимого milestone записать версию 5.0.0, **commit тега** и дату принятия. Использовать [существующий adoption record](../../starter-kit/templates/STANDARD_ADOPTION.md); не придумывать согласования.
3. Обновить весь starter-kit/scripts вместе с lib, vendor tokenizer и его MIT license. Для project records также обновить schemas и REQUIREMENTS.json. Node.js **22+**; POSIX wrappers требуют zsh, Windows wrappers — PowerShell. Синтаксическая проверка JSX не подтверждает ES3/E4X или работу в Adobe host.
4. Routing callers обязаны передавать boolean `product_contract`, `contract_covers_scope`, `changes_product_contract`. Старый единственный flag отвергается. Покрытие scope определяется подтверждённым контрактом и exit criteria, а не наличием файла. Manifest schema **3**, output keys routing не изменены.
5. Project-record schema **1** добавляет optional `phase`: `pre-handoff`, `user-validation`, `release-acceptance`. Schema и validator обновляются вместе: старый strict validator не принимает новый field. Без phase сохраняется прежний gate всех required checks; Release оценивает их все. Выход validator дополняется `deferred_checks`. Выбор обязательных проверок и safety applicability остаётся trusted project policy.
6. Evidence collectors создают новые output paths. Artifact records связывают payload/типы/modes/внутренние symlinks/hashes; verifier не доказывает подлинность записи. Dirty candidates допустимы только для Development; Validation/Release требуют CLEAN. Явно выбрать macOS local/public и required/na stapling policy; Windows timestamp требуется по умолчанию.
7. Перенести цель, решения, разрешения, фактическую Git/artifact identity, blockers и следующий шаг в существующий checkpoint. Проверить затронутый project scope по его acceptance criteria. Не переносить прежний PASS на новые bytes.

## Проверки и границы доказательств

Публикация требует clean source, полного self-test и CI Linux/macOS/Windows на точном commit. Evidence релиза фиксирует revision, jobs и hashes распространяемых архивов; документы не подменяют фактический результат запуска. Источники в SOURCES.md должны укладываться в заявленный freshness interval; дату проверки нельзя просто продлевать.

Проверки scripts/fixtures устанавливают их scoped behavior. Реальные прогоны модели на 20 сценариях **NOT RUN**; ни fixture inspector, ни helper CI не сертифицируют поведение ИИ. Для конкретной AI-конфигурации рекомендуется отдельная оценка с observer traces по [процедуре](../../starter-kit/fixtures/ai/README.md). Product-specific AE runtime также **NOT RUN** в этом релизе правил; внедряющий проект сохраняет собственные применимые host checks.

5.0.0 — первая GitHub Release/tag этого репозитория. Записи 4.0.0 и более ранних версий в CHANGELOG сохраняют историю стандартов; отдельный релиз 4.1.0 не публиковался.
