# AE Development Rules 7.0.0

2026-10-03 · Major release

Вводит CLEANUP-001 / Process §6: при завершении разработки, milestone или подготовки передачи проверить потребность в уборке; если действий не требуется, зафиксировать no-op. Уборка выполняется только в разрешённом scope после проверки сохранности. Это изменение обязательного process contract: compliant 6.x workflow без такой проверки needs review/update, поэтому по Engineering §34 — major, а не minor.

## Протокол и материалы

[Process §6](../../core/PROCESS.md#безопасная-уборка-репозитория-после-разработки) содержит полный план: границы, inventory, concurrent ownership, reviewed action list, реальные пути, preservation/recovery, повторная сверка перед действием, точечная уборка, документы, branches/worktrees, проверки, отчёт и отдельная retention policy.

[Шаблон плана и отчёта](../../starter-kit/templates/REPOSITORY_CLEANUP.md) можно встроить в существующий checkpoint. Smart Entry, Workflow, requirement registry и starter-kit README согласованы. Шесть manual review cases описывают риски, но не являются выполненными model tests.

Неизвестные ownership/purpose/dependencies/permission/recovery — KEEP IN PLACE. Перемещение не считается автоматически безопасным. Git backup не сохраняет ignored/untracked данные. Frozen/released bytes/tag и историческое Evidence не изменяются. Подготовка плана и срок retention не разрешают deletion/purge. Нет обязательного удаления мусора или косметической перестройки там, где они не нужны.

## Adoption и migration

Начните с [AI_ENTRYPOINT.md](../../AI_ENTRYPOINT.md); явно передайте обновлённые правила текущей сессии ИИ. Принятый 6.x baseline остаётся до осознанного adoption по §34. Сначала сравните текущий workflow с CLEANUP-001, добавьте короткую проверку потребности в уборке при завершении и обновите используемые templates/checkpoint.

Новое requirement ID `CLEANUP-001` не меняет manifest schema 3, project-record 1, artifact 2 или command interfaces. Не изменяйте старые Evidence/status задним числом. Проверьте project-owned allowlists/policies, если они перечисляют отдельные requirement IDs. Сохраняются compatibility protocol, platform policy без обязательных certificate services и documentation handoff.

Не запускать удаление только потому, что baseline обновлён. Для фактической уборки нужны ownership/path/dependency/recovery guards и действительное разрешение; сохранить активную работу других сессий. Недоступные обязательные проверки остаются BLOCKED / NOT RUN.

## Verification и сохранность

Exact released commit, PR/main CI, archive hashes и scope записываются после фактического выполнения в GitHub Release / release-evidence.json. Релиз правил не означает, что cleanup в другом продукте выполнен. Actual AI cleanup scenarios и product AE tests: **NOT RUN**.

Предыдущий main/v6.2.0 `d966078a9e45fee7ec9ad14f211a9da753d64b8a` сохраняется в `backup/main-before-v7-release-2026-10-03-d966078` и локальном verified full-history bundle. Прежние tags/releases/assets/backups сохраняются; теги не перемещаются. Откат adopting project восстанавливает собственный прежний baseline и соответствующие tools/records, сохраняя новую работу и Evidence.
