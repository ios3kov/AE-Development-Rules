# Process Core

Нормативный процесс: scope, testing discipline, Git/artifact identity, baseline, regression, Evidence, readiness и workflow boundary.

Нумерация § сохранена глобально для стабильных ссылок из manifest/templates.

## AI Smart Entry prerequisite

При AI-assisted работе сначала применяется [AI_ENTRYPOINT.md](../AI_ENTRYPOINT.md). ИИ самостоятельно классифицирует запрос и выбирает применимые internal rules; пользователь не обязан знать или выбирать Risk Profile / Delivery Gate / Stage 0.

## Reference Audit prerequisite

Если пользователь явно обозначил конкретный внешний продукт/artifact как референс, основу, аналог или parity target, MUST применяться [Reference Audit](../REFERENCE_AUDIT.md) в соответствующем scope.

Для whole-product analogue нельзя начинать Technical Design после поверхностного просмотра UI. Сначала требуется Reference Specification с Coverage Map, evidence-backed claims и parity acceptance tests.

Общее описание класса продукта без конкретного reference target этот prerequisite не включает.

## Stage 0 prerequisite

Перед Product Spec, Technical Design или Production Plan нового продукта / крупной новой функции MUST быть завершён применимый [Stage 0 — Product Discovery и Product Vision](../PRODUCT_DISCOVERY.md).

Stage 0 можно считать уже выполненным, если актуальный подтверждённый Product Vision / requirements contract покрывает текущий scope, включая уже согласованные product-level изменения. Наличие контракта предыдущей версии продукта недостаточно: неподтверждённое изменение пользовательской ценности, core workflows или product scope требует применимого Stage 0 для изменяемой области.

Для локального bugfix/refactor/малой UI-правки Stage 0 повторно не проводится без нового product-level вопроса.

## 1. Применение правил и обязательность проверок

Перед началом каждого значимого этапа сверяться с этим документом, выбирать применимые требования и фиксировать scope проверки. Правила рабочего ритма, статусов этапов и общения находятся в [WORKFLOW.md](../WORKFLOW.md).

Значимый этап:

- research и выбор технического решения;
- реализация функции;
- исправление ошибки;
- архитектурное изменение;
- performance-изменение;
- сборка и упаковка;
- тестирование;
- подготовка milestone / release;
- передача artifact пользователю.

До начала этапа определить:

- цель и критерии приёмки;
- тип инструмента и затронутые компоненты;
- целевые версии After Effects и платформы;
- риски изменения;
- обязательные проверки;
- допустимые отклонения результата;
- необходимые Evidence.

Обязательные проверки определяются заранее, а не после получения результатов.

Нельзя объявлять проверку неприменимой только потому, что она упала или оказалась неудобной.

Изменение набора обязательных проверок должно иметь документированную причину. Если изменение затрагивает согласованные требования или заявленную совместимость, оно должно быть согласовано.

Масштаб процесса должен соответствовать задаче. Не нужно превращать небольшую правку в полный аудит всего продукта, но нельзя сокращать проверки так, чтобы существенные риски оставались без контроля.

### Risk Profile — масштаб и риск изменения

Перед значимым этапом выбрать один Risk Profile. Он определяет глубину инженерных проверок, но **не определяет факт release**.

#### Light

Использовать для:

- небольших локальных исправлений с низким риском;
- documentation-only изменений;
- простых scripts / utilities с ограниченным scope;
- мелких UI-правок без изменения архитектуры или критического поведения.

Минимально требуется:

- определить затронутый scope;
- выполнить релевантные проверки;
- пройти Regression Level 1 для изменений, влияющих на поведение или artifact;
- обновить документацию, если изменение влияет на пользователя или процесс.

Полный Regression Level 2, clean-install cycle и глубокий profiling не требуются автоматически, если соответствующий риск отсутствует.

#### Standard

Использовать для обычной разработки функции, воспроизводимого bugfix или изменения существующего поведения со средним риском.

Обычно требуется:

- зафиксировать baseline;
- определить критерии приёмки и обязательные проверки;
- реализовать изменение;
- пройти Regression Level 1;
- выполнить реальные проверки внутри After Effects для затронутого поведения;
- обновить Evidence и документацию;
- проверить затронутые compatibility/performance сценарии.

#### Critical

Использовать для высокорисковых изменений, например:

- крупных архитектурных изменений;
- render path, MFR / SmartFX, threading, memory ownership;
- security-sensitive logic;
- installer/updater mechanics;
- project-data / migration changes;
- destructive filesystem behavior;
- изменений, способных повредить пользовательские данные или проекты;
- performance-critical изменений с существенным production impact.

Critical требует полного набора проверок **затронутого риска**, обычно включая Regression Level 2, deeper diagnostics/profiling и расширенный recovery/rollback coverage.

Critical сам по себе не требует publication/signing ceremony, пока Delivery Gate остаётся Development или Validation и эти свойства не входят в предмет проверки.

Если во время работы обнаружен более высокий риск, Risk Profile должен быть повышен.

### Delivery Gate — цель передачи

Risk Profile и Delivery Gate выбираются отдельно.

#### Development

Внутренняя работа без передачи artifact пользователю как validation/release.

- применяются требования выбранного Risk Profile;
- Release Gate не запускается автоматически;
- внутренние experiment/diagnostic artifacts должны оставаться идентифицируемыми, если на их Evidence ссылаются.

#### Validation

Ограниченная передача Validation Build для конкретного вопроса UX/runtime/уникального окружения.

- применяется Validation Gate из §26;
- Risk Profile сохраняется независимо;
- полный Release Gate не требуется, если release-only свойства не являются предметом validation.

#### Release

Финальная передача / публикация Release Candidate.

- применяется полный применимый Release Gate из §26;
- platform distribution gates §28/§30 применяются только к соответствующим distributables;
- даже низкорисковый patch release проходит Release Gate, потому что это свойство delivery, а не risk.

### Validation Build и Release Candidate — разные вещи

**Validation Build** — идентифицированный тестовый artifact, передаваемый пользователю для ограниченной проверки UX, поведения или уникального окружения. Он не становится публичным release только из-за факта передачи пользователю.

Для Validation Build по умолчанию требуются:

- понятный scope пользовательской проверки;
- известный commit / Build ID или иная однозначная идентичность artifact;
- релевантные быстрые внутренние проверки;
- отсутствие известных критических проблем безопасности, потери данных и обязательных FAIL для проверяемого сценария;
- явная маркировка, что artifact тестовый и не предназначен для публичного распространения;
- честное перечисление того, что ещё не прошло Release Gate.

Для Validation Build **не требуется автоматически** полный публичный Release Gate, notarization, Authenticode, финальный installer, полный Regression Level 2, полная compatibility matrix или публичный distribution-channel test, если именно эти свойства не являются предметом текущей проверки.

**Release Candidate** — неизменяемый кандидат на финальную передачу / публикацию. Для него выполняется полный применимый Release Gate из §26 и platform-specific gates только там, где они действительно применимы к artifact.

Если цель пользовательского теста — проверить именно финальную установку, подпись, quarantine/SmartScreen, updater или публичный package, соответствующий release/distribution gate становится частью этого теста.

§26 различает Validation Gate и Release Gate. §28 и §30 относятся только к соответствующим публичным platform distributables и не должны механически применяться к каждой внутренней сборке.

### Адаптация для малых команд и solo-разработки

Размер команды сам по себе не является причиной ослаблять требования безопасности, корректности или финального release gate.

Для небольшой команды или одного разработчика:

- использовать режимы Light / Standard / Critical как основной механизм снижения процессного трения;
- объединять роли разработки, review, QA и release допускается, если фактически выполненные проверки и Evidence остаются явными;
- автоматизировать повторяемые проверки раньше, чем добавлять новые ручные ритуалы;
- не требовать отдельный CI/CD сервер, если эквивалентные проверки воспроизводимо запускаются локально одной командой;
- не создавать документы ради документов: достаточно минимальной записи, которая сохраняет решение, результат и Evidence;
- критические проверки, связанные с сохранностью пользовательских данных, runtime-корректностью, artifact identity, compatibility и публичным release, не пропускать из-за размера команды.

Если процесс оказывается слишком тяжёлым для конкретного проекта, сначала уменьшить scope и автоматизировать рутину, а не удалять проверку существенного риска.

### Минимальный профиль для micro-helper

Для однофайлового или очень небольшого helper-скрипта с низким риском, например короткой команды/горячей клавиши без installer, background process, network, project-data migration или destructive filesystem logic, допустим минимальный профиль:

- Git commit или иная однозначно сохранённая версия source;
- syntax / parser sanity-check, где применимо;
- один реальный smoke test в целевой версии After Effects для основного сценария;
- один негативный / безопасный case, если входные условия могут отсутствовать или быть неверными;
- короткая запись результата и известных ограничений.

Для такого micro-helper не требуются отдельная сложная архитектурная документация, полный CI/CD, deep profiling, SBOM или release ceremony, если соответствующие риски отсутствуют.

Если helper начинает хранить состояние, менять проекты массово, работать с файлами/network/helpers или получает существенный user-data/security/performance risk, он выходит из micro-helper profile и переводится в подходящий Standard / Critical режим.

Публичное распространение само по себе переключает Delivery Gate на Release, сохраняя Risk Profile по фактическому риску.

## 2. Контролируемое и чистое тестирование

Каждый тест должен начинаться с известного, контролируемого и воспроизводимого состояния.

Чистое состояние обязательно для сценариев:

- первой установки;
- проверки отсутствия скрытых зависимостей;
- проверки конфликта установленных копий;
- cold-start / cold-cache;
- финальной проверки чистой установки.

Для других сценариев специально подготавливается требуемое состояние:

- обновление с предыдущей версии;
- миграция настроек;
- восстановление сохранённого состояния;
- повторное выполнение;
- warm-cache;
- длительная работа;
- воспроизведение state-dependent ошибки.

Нельзя удалять состояние, необходимое для воспроизведения ошибки, до его фиксации или сохранения.

### Чистое тестовое окружение

В пределах тестового окружения не должно оставаться:

- старых активных сборок;
- конфликтующих версий scripts / extensions;
- установленных копий, способных перехватить запуск;
- кэшей, искажающих конкретный тест;
- временных файлов от предыдущего теста;
- неизвестного сохранённого состояния;
- работающих старых helper-процессов.

Для scripts / panels / CEP / UXP учитывать:

- preferences;
- локальное хранилище;
- runtime-specific caches, где они существуют;
- event listeners;
- timers / polling;
- background processes;
- состояние scripting engine / extension runtime;
- необходимость закрытия панели, reload или перезапуска After Effects.

Новый тест не должен случайно использовать старый artifact или чужое состояние.

### Финальная проверка

Финальная проверка включает:

- чистую установку;
- применимые upgrade / migration сценарии;
- повторный запуск;
- restart After Effects;
- применимые cold-cache и warm-cache сценарии.

Для быстрых внутренних итераций допускается сокращённый цикл, если его ограничения известны и не искажают выводы.

## 3. Research перед разработкой

Перед реализацией новой функции или нового механизма проверить применимые источники:

- Adobe SDK и официальную документацию;
- After Effects scripting API;
- документацию ScriptUI;
- документацию CEP / UXP при подтверждённой применимости;
- release notes и ограничения целевых версий;
- существующие решения;
- open-source;
- похожие plugins / scripts / panels / extensions;
- известные ошибки и ограничения After Effects.

Если проверенное решение существует, сначала оценить возможность его использования или адаптации.

Перед использованием стороннего решения проверить:

- лицензию и условия распространения;
- совместимость с продуктом;
- безопасность;
- поддерживаемость;
- состояние зависимостей;
- ограничения производительности;
- применимость к целевой версии After Effects.

Не копировать код без подходящей лицензии.

Не изобретать собственный механизм без необходимости, если существует подходящий стандартный способ.

Research должен быть соразмерен задаче. Не повторять уже выполненное исследование без новых оснований; использовать актуальную базу знаний проекта.

Значимые решения фиксировать вместе с источниками, ограничениями и причиной выбора.

### Подтверждение используемого host API
<!-- REQ: API-SOURCE-001 -->

При добавлении или изменении обращения к Adobe host API разработчик/ИИ MUST проверить существование API, точную сигнатуру/контракт, suite revision или callback/flag по применимости и доступность для выбранных AE/SDK/OS. Использовать headers реально выбранного SDK и применимую официальную документацию; для scripting/panel API — документацию целевого host/runtime. Отметить противоречия между источниками до зависимого решения.

Ссылку на файл/header/doc section, версию и результат проверки фиксировать в существующем API inventory/research record. Проверенный актуальный inventory можно повторно использовать; документировать каждый неизменённый вызов заново не требуется. [API audit template](../starter-kit/templates/API_COMPATIBILITY_AUDIT.md) содержит поля для такой записи.

Нельзя выдумывать API, suite revision, сигнатуру, callback, flag или переносить API другого Adobe host без подтверждённой применимости. При недостатке источников затронутый API contract остаётся UNKNOWN; зависимый implementation/design блокируется либо выбирается другой подтверждённый способ в пределах согласованного продукта. Независимую работу продолжать. Mock, похожее имя или удачная компиляция не подтверждают host behavior / Compatibility: VERIFIED.

Разрешённое research / изолированный эксперимент для выяснения неизвестного контракта можно продолжать, обозначая гипотезу и границы Evidence. Это не делает недоказанный механизм согласованным production-решением.

## 4. Максимальная автоматизация и безопасность действий
<!-- REQ: SAFE-001 -->

Всё, что можно надёжно и безопасно сделать без участия пользователя, выполнять автоматически.

Не просить пользователя:

- запускать проверки;
- собирать технические данные;
- искать логи;
- копировать файлы;
- устанавливать промежуточные сборки;
- очищать тестовый кэш;
- проверять промежуточные гипотезы,

если разработчик или система разработки могут выполнить это самостоятельно.

### Границы автоматизации

Автоматическая очистка, установка и управление процессами разрешены:

- в выделенном тестовом окружении;
- в принадлежащих тесту каталогах;
- в заранее согласованной области рабочей машины.

Без разрешения нельзя:

- удалять пользовательские preferences;
- удалять проекты или рабочие файлы;
- удалять сторонние plugins / extensions;
- очищать общие данные, не принадлежащие тесту;
- завершать процессы с возможной несохранённой работой;
- менять системные настройки безопасности.

Потенциально разрушительные действия должны иметь:

- ограниченную область воздействия;
- проверку целевого пути или процесса;
- резервную копию или способ восстановления, где применимо;
- понятный журнал выполненных действий.

Автоматизация не должна обходить permissions, sandbox или обязательное согласие пользователя.

### Автоматизация After Effects

Где технически возможно, использовать автоматический запуск AE-тестов.

Для ExtendScript / JSX могут использоваться:

- поддерживаемый command-line запуск скрипта;
- `afterfx -r path/to/test_runner.jsx`, где это поддерживается целевой платформой и версией;
- собственный test runner внутри After Effects.

`afterfx -r` не считать полноценным headless-режимом.

Для render-specific сценариев использовать:

- `aerender`;
- подготовленные test projects;
- автоматическое сравнение render output.

`aerender` не считать универсальной заменой scripting или UI test runner.

Автоматический AE-тест должен по возможности:

1. Подготовить контролируемое окружение.
2. Подтвердить загруженный Build ID.
3. Открыть подготовленный проект.
4. Выполнить тестируемую операцию.
5. Проверить ожидаемый результат.
6. Сохранить output и логи.
7. Записать однозначный статус.
8. Закрыть принадлежащее тесту состояние.

Для автоматических запусков предусмотреть:

- timeout;
- обнаружение crash / hang;
- уникальный Test Run ID;
- отдельные пути результатов;
- защиту от чтения старого PASS-файла;
- безопасную очистку после завершения.

Отсутствие явного результата не считается PASS.

### Практическая автоматизация и CI

Правила не привязаны к конкретному CI/CD продукту. Допустимы GitHub Actions, GitLab CI, Jenkins, Buildkite, локальные scripts или другая система, если она воспроизводимо выполняет требуемые проверки.

Предпочтительно иметь одну понятную entry point команду, например `./scripts/preflight.sh`, которая запускает применимый набор быстрых проверок для текущего проекта.

Для проектов по применимости автоматизировать:

- build / package;
- `git diff --check` и статические проверки;
- unit / integration tests;
- syntax / type checks;
- Build Identity и SHA-256;
- packaging sanity;
- compatibility inventory;
- безопасные non-interactive AE tests;
- release checks, которые технически можно выполнить без ручного UI.

Инструменты выбираются по стеку проекта. Например, pytest допустим для Python tooling, Node test runners / TypeScript для JS/TS, CTest или собственные harnesses для C/C++, но конкретный framework не является обязательным стандартом.

CI должен вызывать те же scripts, которые можно запустить локально, а не содержать отдельную скрытую реализацию проверок.

Автоматизация не должна превращать недоступный runtime test в PASS. Если CI не имеет After Effects или нужной платформы, соответствующая проверка остаётся BLOCKED / NOT RUN.

## 5. Скорость разработки и безопасная параллельность

Всё независимое, что можно безопасно выполнять параллельно, выполнять параллельно:

- research;
- сборки;
- статический анализ;
- независимые автоматические тесты;
- аудит;
- подготовку документации.

Profiling и benchmarks распараллеливать только при отсутствии взаимного влияния на измерения.

Параллельность не должна:

- создавать race conditions;
- смешивать artifacts;
- смешивать логи и test results;
- приводить к тестированию устаревшей сборки;
- менять общее состояние After Effects;
- искажать performance-замеры.

Использовать отдельные:

- build directories;
- Git worktrees, где полезно;
- test workspaces;
- output directories;
- Test Run IDs.

Если тесты используют один экземпляр After Effects или общие preferences, обеспечить изоляцию либо последовательное выполнение.

Скорость достигается автоматизацией и устранением лишней работы, а не отказом от достоверных проверок.

## 6. Git обязателен

Любое изменение исходного кода, конфигурации сборки, тестов и документации должно быть отражено в Git.

Каждый законченный этап должен иметь:

- отдельное логически связное изменение;
- понятный commit;
- возможность определить причину изменения;
- возможность безопасного отката.

Не смешивать несвязанные изменения в одном commit без необходимости.

Перед milestone / release / передачей пользователю:

- изменения зафиксированы;
- рабочее дерево clean;
- нет незадокументированных production-изменений;
- artifact связан с конкретным commit.

Artifacts и крупные Evidence-файлы не обязательно хранить непосредственно в Git. Они должны храниться в надёжном artifact storage с идентификаторами, hash и ссылкой на commit.

Generated files должны иметь определённую политику: отслеживаются в Git либо воспроизводимо создаются и исключены из рабочего дерева.

Не изменять исходники вручную после сборки для «быстрого исправления» передаваемого artifact.

## 7. Build / Artifact Identity
<!-- REQ: ART-001 -->

### Термин Artifact

Artifact — конкретный результат разработки, который устанавливается, запускается или используется в After Effects.

Это может быть:

- `.plugin`;
- `.aex`;
- `.jsx`;
- `.jsxbin`;
- ScriptUI panel;
- CEP extension;
- UXP plugin при подтверждённой поддержке;
- ZIP / installer / package;
- helper executable;
- набор связанных файлов.

### Цепочка идентичности

Для каждого тестируемого artifact должна прослеживаться связь:

**Git commit + source state → Build ID → artifact → SHA-256 → установленный компонент → реально загруженная версия.**

Build metadata должна содержать:

- Git commit;
- состояние clean / dirty;
- Build ID;
- версию инструмента;
- тип artifact;
- целевую платформу / архитектуру, где применимо.

Значимые параметры сборки, версии SDK и toolchain фиксировать в build record.

### Hash

После завершения всех операций, изменяющих распространяемый artifact, автоматически рассчитывать SHA-256.

Такие операции могут включать:

- packaging;
- обфускацию;
- signing;
- stapling;
- другие post-processing steps.

Для многофайлового artifact использовать:

- hash финального package / archive;
- manifest с SHA-256 production-файлов;
- при необходимости оба способа.

Если installer преобразует файлы при установке, отдельно фиксировать проверку установленного payload.

В multi-component package идентифицировать каждый компонент, включая helper-процессы.

### Идентичность реально загруженного кода

Совпадение файла на диске не доказывает, что After Effects загрузил именно его.

Где доступно, подтверждать:

- runtime Build ID;
- путь загруженного компонента;
- Build ID helper-процесса;
- соответствие runtime metadata manifest-файлу.

При необходимости перезапускать After Effects.

### Автоматическое внедрение metadata

Для native effects:

- генерировать metadata через CMake / MSBuild / Xcode или используемую систему сборки;
- показывать Build ID / commit через `PF_Cmd_ABOUT`, где применимо;
- записывать Build ID в начало диагностической сессии.

Для scripts / panels / extensions:

- использовать generated metadata;
- показывать версию в About / Diagnostics;
- записывать identity в диагностический лог.

Build Identity не должен требовать ручного редактирования перед каждой сборкой.

Build ID внутри программы и SHA-256 внешнего artifact — разные идентификаторы. Не создавать циклическую схему, требующую встроить в файл его собственный финальный hash.

### Dirty builds

Dirty build допустим для внутренних экспериментов, но:

- должен быть явно помечен;
- его исходное состояние должно быть восстановимо, если на результат ссылаются;
- он не передаётся пользователю;
- не считается milestone / release;
- его Evidence не заменяет финальную проверку clean artifact.

## 8. Baseline перед изменениями

Перед существенным изменением зафиксировать исходное состояние.

Минимальный baseline:

- что работает;
- что не работает;
- известные ошибки;
- test project / fixture;
- текущий artifact;
- Build ID;
- Git commit;
- воспроизводимый сценарий;
- релевантные результаты и замеры.

Для performance-sensitive изменений дополнительно фиксировать время выполнения и использование ресурсов.

### Native render / effect plugins

По применимости:

- Render performance;
- RAM Preview performance;
- CPU / GPU;
- память;
- MFR;
- cache behaviour;
- bit depth;
- color-management configuration;
- render output.

### Scripts / panels / extensions

По применимости:

- startup time;
- время основных операций;
- UI responsiveness;
- host-call latency;
- file I/O;
- memory behaviour;
- поведение на больших проектах;
- idle-нагрузку.

Для исправления ошибки сначала воспроизвести её на baseline, если это технически возможно.

Если baseline недоступен или ошибка не воспроизводится, явно зафиксировать ограничение. Не представлять предполагаемую причину как доказанную.

## 9. Regression Check — два уровня

### Level 1 — на каждом integration checkpoint / merge-ready commit, затрагивающем поведение или artifact

Выполнять применимые быстрые проверки:

- build / packaging;
- статические проверки;
- unit tests, где доступны;
- запуск;
- основной сценарий;
- smoke tests;
- проверку новых ошибок;
- performance sanity checks для чувствительных изменений.

Для scripts без компиляции под build понимается создание и проверка конечного artifact / package.

Для documentation-only изменений допускается ограничиться проверками документации и её согласованности с проектом.

Если обязательная проверка упала, этап не считается подтверждённым. Нельзя переносить нерешённый FAIL в release gate как будто проверка пройдена.

### Level 2 — перед Release Candidate и по риску для milestone / validation

Для Release Candidate выполнять полный заранее определённый обязательный набор регрессии заявленного scope. Для внутреннего milestone Level 2 требуется только по риску и согласованным acceptance criteria; сам факт milestone его не включает. Для обычного ограниченного Validation Build Level 2 не является автоматическим требованием: его необходимость определяется риском и тем, что именно должен подтвердить пользователь.

- основной функционал;
- затронутые существующие сценарии;
- edge cases;
- error handling;
- повторный запуск;
- сохранение и восстановление состояния;
- restart After Effects;
- применимые upgrade / migration сценарии;
- performance и память;
- совместимость;
- реальные тесты внутри After Effects.

Для native effects и scripts / panels использовать дополнительные проверки из разделов 22–23.

«Полный regression» означает полный заранее определённый обязательный набор, а не все мыслимые комбинации оборудования и настроек.

Новая функция не считается готовой, если она нарушает существующее согласованное поведение.

## 10. Evidence и статусы проверок
<!-- REQ: EVD-001 -->

Утверждения:

- «исправлено»;
- «работает»;
- «ускорено»;
- «проблема устранена»;
- «готово»,

допускаются только в пределах имеющихся подтверждений.

### Допустимые Evidence

- автоматический тест;
- integration test;
- реальный тест в After Effects;
- лог с проверяемым результатом;
- benchmark;
- profiler capture;
- screenshot;
- video capture;
- сравнение output;
- hash;
- воспроизводимый test report.

### Evidence должно соответствовать утверждению

- Hash подтверждает идентичность, а не корректность.
- Успешная компиляция подтверждает сборку, а не рабочее поведение.
- Screenshot подтверждает видимый результат, а не отсутствие утечки памяти.
- Smoke test подтверждает проверенный сценарий, а не всю совместимость.
- Benchmark подтверждает производительность в указанных условиях.

Анализ кода сам по себе не является доказательством исправления runtime-проблемы.

### Единая таксономия статусов

Использовать три независимых namespace. Не смешивать их в одной колонке или формулировке.

**Test Status** — результат конкретно выполненной проверки:

- **PASS** — выполнена, критерии соблюдены.
- **FAIL** — выполнена, критерии нарушены.
- **BLOCKED** — выполнение невозможно из-за конкретного препятствия.
- **NOT RUN** — не запускалась.
- **N/A** — неприменима; указана причина.

`BLOCKED`, `NOT RUN` и `N/A` не являются PASS.

**Compatibility Status** — уровень подтверждения конкретной конфигурации / версии:

- **VERIFIED** — реально запущена и проверена в заявленном runtime scope.
- **STATIC-COMPATIBLE** — статический audit не нашёл известных препятствий, но runtime test не выполнен.
- **LIMITED** — поддерживается только в явно указанном ограниченном scope.
- **UNSUPPORTED** — найдено конкретное несовместимое требование / API / binary / platform limitation.
- **UNKNOWN** — данных недостаточно.

**Evidence Confidence** — качество основания для инженерного утверждения или know-how:

- **PROVEN** — подтверждено воспроизводимым test/runtime evidence.
- **USER-REPORTED** — наблюдение подтверждено пользователем в его среде, но не воспроизведено независимо.
- **OBSERVED** — исследовательское наблюдение / диагностика с ограниченным scope.
- **UNVERIFIED** — предположение или вопрос без достаточного подтверждения.

Если контекст может быть неоднозначным, писать namespace явно: `Test: PASS`, `Compatibility: VERIFIED`, `Evidence: PROVEN`.

При необходимости известную ожидаемую ошибку можно отмечать дополнительным признаком, но это не должно скрывать её фактический Test Status или делать обязательный gate успешным.

### Test record

Для значимой проверки сохранять:

- Test Run ID;
- проверяемое утверждение;
- Build ID и artifact hash;
- окружение;
- входные данные;
- начальное состояние;
- шаги или версию test runner;
- ожидаемый результат;
- фактический результат;
- статус;
- ссылки на Evidence;
- ограничения проверки.

Вывод не должен быть шире проверки.

Предпочтительная формулировка:

> В проверенном наборе сценариев регрессий не обнаружено.

Не использовать абсолютное «регрессий нет» как заявление о всех возможных условиях.

## 11. Критерии завершения и готовности

Различать:

- **реализация завершена** — изменения кода выполнены;
- **готово к validation** — Validation Gate пройден для явно ограниченного пользовательского теста;
- **проверка завершена** — обязательные проверки заявленного scope выполнены и результаты зафиксированы;
- **готово к release** — полный применимый Release Gate пройден для Release Candidate;
- **выпущено** — проверенный Release Candidate опубликован или передан установленным способом.

Задача не считается полностью завершённой только потому, что код написан.

Для полного завершения:

- требование реализовано;
- artifact создан;
- основной сценарий реально проверен;
- Regression Level 1 пройден;
- обязательные критерии приёмки выполнены;
- нет известных критических ошибок;
- относящиеся к инструменту warnings / errors исследованы;
- документация актуальна;
- изменения находятся в Git;
- Build / Artifact Identity известен;
- Evidence сохранено;
- для performance-critical изменений есть реальные замеры.

Для ограниченного Validation Build дополнительно:

- пройден Validation Gate из §26;
- зафиксирован scope пользовательской проверки;
- проверен именно передаваемый тестовый artifact.

Для внутреннего milestone:

- закрыты заранее определённые milestone acceptance criteria;
- пройдена регрессия по риску и scope;
- Evidence относится к идентифицированному результату milestone.

Для Release Candidate дополнительно:

- пройден Regression Level 2;
- пройден полный применимый Release Gate;
- проверен именно финальный кандидат.

Milestone не переключает Delivery Gate автоматически.

### Когда проверка недоступна

Если нет доступа к After Effects, требуемой платформе, GPU, лицензии или runtime:

- указать статус `BLOCKED` или `NOT RUN`;
- описать непроверенный сценарий;
- указать причину;
- определить условие разблокировки.

Реализация может быть завершена, но непроверенный обязательный сценарий не считается подтверждённым.

Нельзя подменять реальное AE-тестирование mock-тестом или анализом кода без явного указания ограничения.

## 12. Один источник подтверждённого состояния

Код, Git, artifact, документация и результаты тестов не должны противоречить друг другу.

Подтверждённое состояние проекта определяется связкой:

**Проверенный commit + идентифицированный artifact + относящееся к нему Evidence.**

Документация должна различать:

- текущее состояние разработки;
- последний проверенный milestone;
- последний release.

Нельзя писать «готово к validation» или «готово к release» без указания соответствующего scope и gate.

Нельзя объявлять artifact готовым к заявленной передаче, если:

- относящиеся к передаче изменения не зафиксированы и artifact нельзя однозначно воспроизвести;
- тестировался другой artifact;
- Build ID / artifact identity неизвестны;
- Evidence относится к другой версии;
- обязательные для заявленного Validation Gate или Release Gate проверки не пройдены;
- документация / инструкция описывает другое поведение.

Test reports и release records предпочтительно хранить отдельно от генерируемых исходников, чтобы запись результата проверки не требовала изменения уже проверенного production artifact.

Исторические Evidence не переписывать под новую версию. Создавать новую запись проверки.

---

## 13. Не менять рабочую архитектуру без необходимости

Не переписывать рабочую архитектуру только потому, что другой вариант:

- красивее;
- современнее;
- моднее;
- теоретически «правильнее».

Архитектурное изменение допустимо при обоснованной причине:

- bug;
- limitation;
- performance bottleneck;
- incompatibility;
- security issue;
- проблема поддержки;
- невозможность дальнейшего развития;
- существенное упрощение;
- измеримая или проверяемая польза.

Перед существенным изменением:

- зафиксировать проблему;
- рассмотреть менее рискованные варианты;
- определить затронутое поведение;
- подготовить regression coverage;
- определить способ отката.

Не смешивать исправление ошибки с широким рефакторингом без необходимости.

Рабочее поведение не должно становиться случайной жертвой архитектурных улучшений.
