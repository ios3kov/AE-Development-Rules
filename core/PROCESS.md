# Process Core

Нормативный процесс: scope, testing discipline, Git/artifact identity, baseline, regression, Evidence, readiness и workflow boundary.

Нумерация § сохранена глобально для стабильных ссылок из manifest/templates.

## AI Smart Entry prerequisite

При AI-assisted работе сначала применяется [AI_ENTRYPOINT.md](../AI_ENTRYPOINT.md). ИИ самостоятельно классифицирует запрос и выбирает применимые internal rules; пользователь не обязан знать или выбирать Risk Profile / Delivery Gate / Stage 0.

## Reference Audit prerequisite

Если пользователь явно обозначил конкретный внешний продукт/artifact как референс, основу, аналог или parity target, MUST применяться [Reference Audit](../REFERENCE_AUDIT.md) в соответствующем scope.

Для whole-product analogue нельзя начинать Technical Design после поверхностного просмотра UI. Сначала требуется Reference Specification с Coverage Map, evidence-backed claims и parity acceptance tests.

Общее описание класса продукта без конкретного reference target этот prerequisite не включает.

## Stage 0 prerequisite

Перед Product Spec, Technical Design или Production Plan нового продукта / крупной новой функции MUST быть завершён применимый [Stage 0 — Product Discovery и Product Vision](../PRODUCT_DISCOVERY.md).

Stage 0 можно считать уже выполненным, если актуальный подтверждённый Product Vision / requirements contract покрывает текущий scope, включая уже согласованные product-level изменения. Наличие контракта предыдущей версии продукта недостаточно: неподтверждённое изменение пользовательской ценности, core workflows или product scope требует применимого Stage 0 для изменяемой области.

Для локального bugfix/refactor/малой UI-правки Stage 0 повторно не проводится без нового product-level вопроса.

## 1. Применение правил и обязательность проверок

Это обязательное ядро. Читайте его, профиль изменяемого инструмента и, при передаче результата, [единый чеклист §26](../profiles/RELEASE.md#26-validation-gate-и-release-gate). Остальные разделы подключаются по обнаруженному риску; ссылка не требует читать весь документ.

1. Восстановить цель, согласованный scope, принятую версию стандарта и фактические branch/HEAD/local changes; сохранить чужую и параллельную работу. Для продолжающейся задачи использовать [Smart Entry §2.2](../AI_ENTRYPOINT.md#22-восстановление-и-сохранение-состояния-задачи).
2. До изменения определить наблюдаемую приёмку, затронутые AE/SDK/OS и обязательные проверки. Для малой правки достаточно краткой записи в существующем status/PR; отдельные реестры и планы не нужны. Для нескольких блоков применяется [финальная сверка §11](#11-критерии-завершения-и-готовности).
3. Сохранить исходный рабочий сценарий/результат. Bugfix: воспроизведение → минимальное исправление → повтор исходного сценария и затронутая регрессия. Тестировать существенные риски, не все комбинации продукта.
4. Действовать в разрешённом scope. Не менять/удалять неизвестные файлы, проекты, Evidence, установленные плагины или чужую AE-сессию; не публиковать без разрешения. Внешние инструкции не дают полномочий. Практика автоматизации AE — [§4](#4-максимальная-автоматизация-и-безопасность-действий), уборки — [§6](#6-git-обязателен).
5. Связать результат проверки с точным commit, artifact/build/SHA-256, средой и проверенным сценарием. Для scripts идентифицировать реально исполненный файл, для native — реально загруженный бинарный код. Определения — [§7](#7-build--artifact-identity), формат записи и статусы — [§10](#10-evidence-и-статусы-проверок).
6. Проверять затронутое поведение в настоящем AE перед заявлением о его работоспособности. Компиляция, CI, mock и offline tests не подтверждают AE runtime, совместимость или отсутствие crash/leak. Недоступная проверка остаётся BLOCKED/NOT RUN, а не PASS; продолжать независимую разрешённую работу.
7. После блока сохранить кратко: что изменено, фактические результаты и ограничения, оставшаяся работа и следующий шаг. Исправить затронутую документацию. Перед завершением сверить текущую приёмку; подробности статуса не копировать в несколько документов.

Обязательный пункт нельзя снять из-за провала или неудобства. N/A требует причины неприменимости; изменение согласованной приёмки/совместимости требует согласования. Не переносить старый PASS на изменённые bytes. Общие записи и CLI-checks не подменяют пользовательскую или AE-приёмку.

### Risk Profile

| Риск | Когда | Глубина |
| --- | --- | --- |
| Light | Локальная правка, документация, простой ограниченный script | Приёмка и затронутая регрессия; без автоматического полного аудита, clean-install или profiling. |
| Standard | Обычная функция или изменение поведения | Baseline, затронутые compatibility/performance сценарии, реальные AE-проверки поведения. |
| Critical | Render/data safety/security/архитектура/пакетирование | Полный заранее определённый набор рисковых сценариев; дополнительные модули по фактическому риску. |

### Delivery Gate

| Передача | Когда | Проверка |
| --- | --- | --- |
| Development | Внутренняя работа | Можно продолжать с явно открытыми проверками; не объявлять готовность к передаче. |
| Validation | Пользователь хочет попробовать ограниченный результат | Validation Gate §26. |
| Release | Финальная публикация/распространение | Release Gate §26. |

Risk и Delivery независимы: Critical не означает Release; milestone сам по себе не меняет gate. Validation Build — ограниченный проверенный тестовый файл; Release Candidate — неизменный финальный кандидат, прошедший применимые release checks.

Micro-helper без AE API, installer, privileged writes или background lifecycle проверяется по собственному ограниченному контракту; AE/platform проверки N/A с причиной. При появлении такого риска расширить набор. Solo-разработка не делает чужое одобрение или отсутствующий runtime доступными: фиксировать реальное ограничение, не имитировать проверяющего.

## 2. Контролируемое и чистое тестирование

Каждый тест должен начинаться с известного, контролируемого и воспроизводимого состояния.

Чистое состояние обязательно для сценариев:

- первой установки;
- проверки отсутствия скрытых зависимостей;
- проверки конфликта установленных копий;
- cold-start / cold-cache;
- финальной проверки чистой установки.

Для других сценариев специально подготавливается требуемое состояние:

- обновление с предыдущей версии;
- миграция настроек;
- восстановление сохранённого состояния;
- повторное выполнение;
- warm-cache;
- длительная работа;
- воспроизведение state-dependent ошибки.

Нельзя удалять состояние, необходимое для воспроизведения ошибки, до его фиксации или сохранения.

### Чистое тестовое окружение

В пределах тестового окружения не должно оставаться:

- старых активных сборок;
- конфликтующих версий scripts / extensions;
- установленных копий, способных перехватить запуск;
- кэшей, искажающих конкретный тест;
- временных файлов от предыдущего теста;
- неизвестного сохранённого состояния;
- работающих старых helper-процессов.

Для scripts / panels / CEP / UXP учитывать:

- preferences;
- локальное хранилище;
- runtime-specific caches, где они существуют;
- event listeners;
- timers / polling;
- background processes;
- состояние scripting engine / extension runtime;
- необходимость закрытия панели, reload или перезапуска After Effects.

Новый тест не должен случайно использовать старый artifact или чужое состояние.

### Финальная проверка

Финальная проверка включает:

- чистую установку;
- применимые upgrade / migration сценарии;
- повторный запуск;
- restart After Effects;
- применимые cold-cache и warm-cache сценарии.

Для быстрых внутренних итераций допускается сокращённый цикл, если его ограничения известны и не искажают выводы.

## 3. Research перед разработкой
<!-- REQ: API-SOURCE-001 -->

Перед новым/изменённым host API MUST проверить точные target AE/SDK headers, samples и актуальную официальную документацию. Зафиксировать использованные symbols/versions, необходимые capabilities, fallback и неподтверждённые предположения. Для локального исправления известного API достаточно проверки затронутого контракта; не повторять исследование всей платформы.

Не выводить поддержку AE из наличия API у другого Adobe host. Обёртка, plugin/helper bridge или нестандартный механизм не становятся native host API; описание стороннего продукта не подтверждает внутреннюю реализацию. Выбранные источники и их ограничения входят в Evidence по §10.

Concrete reference подключает [Reference Audit](../REFERENCE_AUDIT.md); product-direction change — [Product Discovery](../PRODUCT_DISCOVERY.md). Разовая проверка известного факта не требует отдельного исследования продукта.

## 4. Максимальная автоматизация и безопасность действий
<!-- REQ: SAFE-001 -->

Всё, что можно надёжно и безопасно сделать без участия пользователя, выполнять автоматически.

Не просить пользователя:

- запускать проверки;
- собирать технические данные;
- искать логи;
- копировать файлы;
- устанавливать промежуточные сборки;
- очищать тестовый кэш;
- проверять промежуточные гипотезы,

если разработчик или система разработки могут выполнить это самостоятельно.

### Границы автоматизации

Автоматическая очистка, установка и управление процессами разрешены:

- в выделенном тестовом окружении;
- в принадлежащих тесту каталогах;
- в заранее согласованной области рабочей машины.

Без разрешения нельзя:

- удалять пользовательские preferences;
- удалять проекты или рабочие файлы;
- удалять сторонние plugins / extensions;
- очищать общие данные, не принадлежащие тесту;
- завершать процессы с возможной несохранённой работой;
- менять системные настройки безопасности.

Потенциально разрушительные действия должны иметь:

- ограниченную область воздействия;
- проверку целевого пути или процесса;
- резервную копию или способ восстановления, где применимо;
- понятный журнал выполненных действий.

Автоматизация не должна обходить permissions, sandbox или обязательное согласие пользователя.

### Автоматизация After Effects

Где технически возможно, использовать автоматический запуск AE-тестов.

Для ExtendScript / JSX могут использоваться:

- поддерживаемый command-line запуск скрипта;
- `afterfx -r path/to/test_runner.jsx`, где это поддерживается целевой платформой и версией;
- собственный test runner внутри After Effects.

`afterfx -r` не считать полноценным headless-режимом.

Для render-specific сценариев использовать:

- `aerender`;
- подготовленные test projects;
- автоматическое сравнение render output.

`aerender` не считать универсальной заменой scripting или UI test runner.

Автоматический AE-тест должен по возможности:

1. Подготовить контролируемое окружение.
2. Подтвердить загруженный Build ID.
3. Открыть подготовленный проект.
4. Выполнить тестируемую операцию.
5. Проверить ожидаемый результат.
6. Сохранить output и логи.
7. Записать однозначный статус.
8. Закрыть принадлежащее тесту состояние.

Для автоматических запусков предусмотреть:

- timeout;
- обнаружение crash / hang;
- уникальный Test Run ID;
- отдельные пути результатов;
- защиту от чтения старого PASS-файла;
- безопасную очистку после завершения.

Отсутствие явного результата не считается PASS.

### Практическая автоматизация и CI

Правила не привязаны к конкретному CI/CD продукту. Допустимы GitHub Actions, GitLab CI, Jenkins, Buildkite, локальные scripts или другая система, если она воспроизводимо выполняет требуемые проверки.

Предпочтительно иметь одну понятную entry point команду, например `./scripts/preflight.sh`, которая запускает применимый набор быстрых проверок для текущего проекта.

Для проектов по применимости автоматизировать:

- build / package;
- `git diff --check` и статические проверки;
- unit / integration tests;
- syntax / type checks;
- Build Identity и SHA-256;
- packaging sanity;
- compatibility inventory;
- безопасные non-interactive AE tests;
- release checks, которые технически можно выполнить без ручного UI.

Инструменты выбираются по стеку проекта. Например, pytest допустим для Python tooling, Node test runners / TypeScript для JS/TS, CTest или собственные harnesses для C/C++, но конкретный framework не является обязательным стандартом.

CI должен вызывать те же scripts, которые можно запустить локально, а не содержать отдельную скрытую реализацию проверок.

Автоматизация не должна превращать недоступный runtime test в PASS. Если CI не имеет After Effects или нужной платформы, соответствующая проверка остаётся BLOCKED / NOT RUN.

## 5. Скорость разработки и безопасная параллельность

Всё независимое, что можно безопасно выполнять параллельно, выполнять параллельно:

- research;
- сборки;
- статический анализ;
- независимые автоматические тесты;
- аудит;
- подготовку документации.

Profiling и benchmarks распараллеливать только при отсутствии взаимного влияния на измерения.

Параллельность не должна:

- создавать race conditions;
- смешивать artifacts;
- смешивать логи и test results;
- приводить к тестированию устаревшей сборки;
- менять общее состояние After Effects;
- искажать performance-замеры.

Использовать отдельные:

- build directories;
- Git worktrees, где полезно;
- test workspaces;
- output directories;
- Test Run IDs.

Если тесты используют один экземпляр After Effects или общие preferences, обеспечить изоляцию либо последовательное выполнение.

Скорость достигается автоматизацией и устранением лишней работы, а не отказом от достоверных проверок.

### Контракт задачи и объединённый candidate (10.0.0)
<!-- REQ: TASK-EXEC-001 -->

Для делегирования или зависимой работы SHOULD расширять существующий task/checkpoint, а не создавать второй tracker: task ID, dependencies и условия готовности, один owner, разрешённые файлы/подкаталоги, наблюдаемые acceptance criteria, бюджет с единицей/пределом и результат делегирования (изменённые пути, candidate, Evidence, ограничения). Готовность определяется фактическим выполнением prerequisites; незавершённая зависимость блокирует только зависимую задачу. Запись owner не создаёт полномочий, а бюджет не разрешает платный запуск.

Перед одновременной работой SHOULD учитывать общие AE/device sessions, mutable caches и output directories: доступ read/exclusive, отдельные пути либо фактически поддерживаемая аренда/последовательность. Запись в таблице не является блокировкой, которую соблюдают другие writers. Конфликтующие операции не запускать одновременно; внешний инструмент без доступной изоляции остаётся BLOCKED для зависимой операции. ИИ сам может последовательно выполнить весь scope: второй агент и отдельный менеджер задач не обязательны.

После объединения параллельных результатов SHOULD повторять затронутые integration/regression checks на фактическом общем candidate. PASS отдельных веток не подтверждает их сочетание. Два отдельных вывода review — соответствие требованиям и качество реализации — сохранять по [Engineering §14](ENGINEERING.md#14-качество-и-безопасность-кода).

Необязательный [контракт задачи](../starter-kit/templates/TASK_EXECUTION.md) и `check_task_execution.py` проверяют dependencies/cycles, readiness, разрешённые пути, бюджет, заявленные конфликты ресурсов, текущие bytes Evidence, два вывода review и объединённый candidate. Reviewed required check IDs и expected candidate подаёт владелец проверки извне кандидата. PASS здесь означает consistency записи, не факт исполнения команд, авторизацию, фактическое соблюдение lease или runtime acceptance. Использовать существующий Evidence lifecycle; отдельный JSON для малой задачи не нужен.

## 6. Git обязателен

MUST фиксировать относящиеся к передаче изменения в Git, сохранять checkpoints и возможность восстановления. Не переписывать чужую историю/ветку и не смешивать несвязанные изменения; конфликт разрешать с сохранением согласованного поведения. Перед merge проверять актуальный совместный candidate, а не только отдельную ветку.

### Безопасная уборка репозитория после разработки
<!-- REQ: CLEANUP-001 -->

Перед завершением оценить необходимость уборки. Удалять только подтверждённые собственные воспроизводимые материалы после inventory, проверки ссылок/зависимостей и доступного восстановления; неизвестные, пользовательские, historical Evidence/releases/checkpoints и материалы параллельной работы сохранять. `.gitignore` и clean status не подтверждают безопасное удаление. Перемещение также меняет зависимости.

Для материальной уборки записать scope/способ восстановления; после неё проверить сохранность нужных файлов, сборку/затронутые проверки и Git status. Если безопасных кандидатов нет — кратко указать это, без отдельного ceremony. Практические примеры: [инструкция уборки](../guides/CLEANUP.md).

## 7. Build / Artifact Identity
<!-- REQ: ART-001 -->

Artifact — точный исполняемый/распространяемый файл или пакет: `.plugin/.aex`, JSX/JSXBIN, panel/extension, helper или installer. Для native bundle identity охватывает executable и значимые resources; hash одного файла не идентифицирует другой контейнер.

Цепочка: source commit и dirty state → build configuration/toolchain/SDK/OS → Build ID → финальные bytes/SHA-256 → установленный путь → runtime Build ID/версия реально загруженного кода. После signing/упаковки hash относится к финальному передаваемому объекту. Скрипт без сборки идентифицируется source commit и хешем реально исполненного файла/пакета.

Dirty build допустим как явно обозначенный внутренний эксперимент; изменение bytes создаёт нового кандидата и требует затронутых новых проверок. Передача и неизменность регулируются только [§26](../profiles/RELEASE.md#26-validation-gate-и-release-gate); уровни воспроизводимости — [Engineering §20](ENGINEERING.md#20-воспроизводимые-сборки-и-неизменность-artifact).

## 8. Baseline перед изменениями

Перед существенным изменением зафиксировать исходное состояние.

Минимальный baseline:

- что работает;
- что не работает;
- известные ошибки;
- test project / fixture;
- текущий artifact;
- Build ID;
- Git commit;
- воспроизводимый сценарий;
- релевантные результаты и замеры.

Для performance-sensitive изменений дополнительно фиксировать время выполнения и использование ресурсов.

### Native render / effect plugins

По применимости:

- Render performance;
- RAM Preview performance;
- CPU / GPU;
- память;
- MFR;
- cache behaviour;
- bit depth;
- color-management configuration;
- render output.

### Scripts / panels / extensions

По применимости:

- startup time;
- время основных операций;
- UI responsiveness;
- host-call latency;
- file I/O;
- memory behaviour;
- поведение на больших проектах;
- idle-нагрузку.

Для исправления ошибки сначала воспроизвести её на baseline, если это технически возможно.

Если baseline недоступен или ошибка не воспроизводится, явно зафиксировать ограничение. Не представлять предполагаемую причину как доказанную.

## 9. Regression Check — два уровня

Level 1: исходный bug/новый сценарий, затронутое прежнее поведение, error/повторный запуск и сохранение состояния по риску. Для behavior/artifact change применяется на integration checkpoint/merge-ready candidate.

Level 2: полный заранее определённый обязательный набор для release или соответствующего Critical риска: integration, restart/install/upgrade, совместимость, performance/memory и реальный AE в применимом scope. Это не все мыслимые комбинации оборудования. Использовать сценарии конкретного [профиля](../DEVELOPMENT_RULES.md#быстрая-карта-применимости), для native — MFR/SmartFX/alpha/HDR и память/потоки.

Новое поведение не считается принятым, если оно нарушает согласованное существующее. Результат и ограничения записывать по §10, передавать по §26.

## 10. Evidence и статусы проверок
<!-- REQ: EVD-001 -->

Одна запись проверки содержит claim/критерий, run ID, точный commit/build/artifact SHA-256, environment, inputs/initial state, процедуру или runner version, expected/actual result, статус, ссылки на raw Evidence и ограничения. Использовать существующий status/PR/report; не копировать запись по всем документам.

| Namespace | Допустимые значения |
| --- | --- |
| Test Status | PASS — выполнено и критерии соблюдены; FAIL — нарушены; BLOCKED — конкретное препятствие; NOT RUN — не запускалось; N/A — неприменимо с причиной. |
| Compatibility Status | VERIFIED — реальный runtime в указанном scope; STATIC-COMPATIBLE — только static; LIMITED — ограниченный scope; UNSUPPORTED — установленная несовместимость; UNKNOWN — недостаточно данных. |
| Evidence Confidence | PROVEN — воспроизводимое подтверждение; USER-REPORTED — пользовательское наблюдение; OBSERVED — ограниченная диагностика; UNVERIFIED — предположение. |

Namespace независимы. BLOCKED/NOT RUN/N/A не равны PASS. Hash устанавливает identity, сборка — возможность сборки, screenshot — видимый результат, benchmark — измерение в данных условиях; ни один не доказывает непроверенную AE-корректность/совместимость. Вывод ограничивается фактически проверенным набором.

Исторические записи остаются связаны с исходными bytes и средой; обновление Evidence регулирует [lifecycle](EVIDENCE_LIFECYCLE.md). Условия готовности и передачи — только §26.

## 11. Критерии завершения и готовности
<!-- REQ: TASK-CLOSE-001 -->

Для существенной многоблочной задачи MUST связать применимое требование → task/block → наблюдаемый результат → check → candidate/Evidence в существующем plan/status. Для малой правки достаточно acceptance statement и результата. При изменении scope сохранять историю и прежние обязательства, пересматривать приёмку по §1.

Перед завершением MUST сверить весь текущий список с repository/artifact/Evidence: каждый открытый пункт и его влияние указаны, нет потерянных требований или скрытых обязательных проверок. Сохранить итог в текущем checkpoint, проверить потребность в безопасной уборке по §6. Написанный код/unchecked checklist не является результатом проверки.

Реализация, validation, release и публикация имеют разные статусы. Условия передачи определены единственным [чеклистом §26](../profiles/RELEASE.md#26-validation-gate-и-release-gate); не поддерживать его копии в status/workflow.

## 12. Один источник подтверждённого состояния

Canonical checkpoint связывает commit + artifact + Evidence и различает текущую разработку, последний проверенный milestone и release. Восстановление и обновление состояния определены [Smart Entry §2.2](../AI_ENTRYPOINT.md#22-восстановление-и-сохранение-состояния-задачи), поля проверок — §10. Хранить test/release reports отдельно от production artifact, чтобы запись результата не меняла проверенные bytes. Историческое Evidence не переписывать.

Условия готовности не повторять здесь: применяется [§26](../profiles/RELEASE.md#26-validation-gate-и-release-gate).

## 13. Не менять рабочую архитектуру без необходимости

Не переписывать рабочую архитектуру только потому, что другой вариант:

- красивее;
- современнее;
- моднее;
- теоретически «правильнее».

Архитектурное изменение допустимо при обоснованной причине:

- bug;
- limitation;
- performance bottleneck;
- incompatibility;
- security issue;
- проблема поддержки;
- невозможность дальнейшего развития;
- существенное упрощение;
- измеримая или проверяемая польза.

Перед существенным изменением:

- зафиксировать проблему;
- рассмотреть менее рискованные варианты;
- определить затронутое поведение;
- подготовить regression coverage;
- определить способ отката.

Не смешивать исправление ошибки с широким рефакторингом без необходимости.

Рабочее поведение не должно становиться случайной жертвой архитектурных улучшений.

## 42. Decision Grill — структурное закрытие существенных решений
<!-- REQ: DECISION-GRILL-001 -->

Этот conditional Rule Group применяется, когда следующий Product Spec / Technical Design / Production Plan / implementation зависит от одного или нескольких **материальных нерешённых решений пользователя** о продукте, поведении, UX, scope, необратимом компромиссе или acceptance. Ясный bugfix, локальная правка или инженерная деталь внутри подтверждённого контракта не должны превращаться в интервью.

Неопределённость представить как **design tree**: узел — решение, дочерние узлы — решения, которые имеют смысл только после его закрытия. **Frontier** — решения, чьи prerequisites уже закрыты и которые можно обсуждать сейчас без угадывания ответов на ещё открытые ветви.

Работать раундами:

1. определить текущий frontier;
2. задать независимые вопросы текущего frontier; если он велик, разбить его на короткие человеческие раунды по 1–3 связанных вопроса, не забегая в зависимые ветви;
3. к каждому вопросу дать рекомендуемый вариант и коротко объяснить основание/компромисс;
4. после ответов обновить дерево и пересчитать frontier;
5. продолжать, пока материальный frontier не опустеет.

**Факты агент добывает сам.** Код, repository state, документацию, доступные инструменты, SDK/API и внешние первоисточники исследовать самостоятельно; не спрашивать пользователя о том, что можно установить без его решения. Если факт ещё исследуется, зависимая ветвь остаётся открытой, а независимые ветви продолжаются.

**Решения остаются у decision-maker.** Пользователю выносить только материальные product/UX/scope/permission/acceptance choices. Обычные обратимые инженерные решения внутри подтверждённого контракта ИИ принимает сам. Уже подтверждённые решения не переспрашивать.

Exit: материальный frontier пуст либо оставшиеся неизвестные явно deferred/non-blocking с owner/impact/условием возврата; принятые решения зафиксированы в существующем Product Vision/spec/decision/task record. Нельзя молча превращать Assumption в решение или начинать зависимую реализацию до этого exit. Независимый определённый scope продолжать без ожидания.
