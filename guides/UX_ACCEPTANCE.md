# Проверяемое качество UX и визуального результата

Практическое дополнение к [Product Discovery](../PRODUCT_DISCOVERY.md), Engineering §39 и [приёмке](../profiles/RELEASE.md#26-validation-gate-и-release-gate). Новых универсальных gates, numeric thresholds и обязательного интервью для bugfix нет.

Для нового или существенно меняющегося UI/визуального эффекта использовать существующую product acceptance, а не оценку «выглядит профессионально».

## Ранний образец

Подготовить небольшой прототип основного сценария или representative render до массовой реализации. Связать его с согласованной задачей пользователя, примерами expected output и полезными defaults/presets. При существенном выборе поведения/внешнего вида показать вариант и конкретный компромисс; уже согласованное решение не переспрашивать. Собственный прототип не становится внешним parity target автоматически.

## Что наблюдать

| Область | Пример проверяемой приёмки |
| --- | --- |
| Основное действие | Пользователь получает нужный результат понятной последовательностью; предел действий выбирается продуктом |
| Состояния | Нужные empty/loading/error/cancel/retry состояния понятны и сохраняют проект |
| Layout | Основные controls доступны при согласованном размере панели, scaling и длине подписей |
| Responsiveness | Измерена задержка нужной операции; нет ненужной idle-нагрузки; бюджет определён сценарием |
| Визуальный эффект | Defaults дают ожидаемый полезный результат на выбранных fixtures, включая нужные alpha/HDR и крайние значения |
| Завершённость | Реальное установленное поведение, labels, tooltips, инструкция и фактический scope согласованы |

Сохранить prototype/candidate identity, fixture, expected/actual и замечания в текущей приёмке. Макет или screenshot подтверждает только видимое состояние, не loading/cancel/Undo или SDK-поведение. Исправить блокирующие замечания и повторить затронутую проверку. Вкусовое предпочтение не объявлять техническим дефектом без согласованного критерия.

Полезный ранний образец уменьшает риск реализации неверного решения; его наличие само по себе не доказывает ускорение разработки. Такой цикл не требуется для каждой внутренней технической правки.
