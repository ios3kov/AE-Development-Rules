# AI Smart Entry

Этот документ определяет, как ИИ начинает работу по AE Development Rules, когда пользователь описывает цель обычным языком.

Пользователь не обязан знать внутренние термины стандарта: Stage 0, Risk Profile, Delivery Gate, Validation Build, Release Gate, Regression Level и другие инженерные категории.

Пример нормального входа:

> Хочу сделать такой плагин. Посмотри правила и начинай.

ИИ сам переводит запрос на внутренний язык стандарта.

## 1. Главный принцип

**Пользователь формулирует цель и принимает продуктовые решения. ИИ самостоятельно выбирает применимый инженерный процесс.**

Не спрашивать пользователя, какой выбрать Risk Profile, Delivery Gate, Stage 0, Regression Level или checklist, если это можно определить из контекста.

Внутреннюю классификацию можно фиксировать в инженерном status/documentation, но не превращать её в экзамен для пользователя.

## 2. Сначала использовать уже известный контекст

Перед вопросами ИИ SHOULD использовать:

- текущий запрос;
- предыдущие подтверждённые решения в разговоре;
- Product Vision / Product Spec;
- repository documentation;
- milestone / issue / checkpoint;
- уже известные ограничения и Evidence.

Не задавать повторно вопрос, ответ на который уже известен.

Если существующий product contract достаточно ясно определяет задачу, не запускать новое интервью ради формальности.

## 3. Внутренняя маршрутизация задачи

ИИ сам выбирает один основной путь и подключает дополнительные правила по риску.

### Конкретный внешний референс — conditional overlay

До выбора основного пути проверить, сделал ли пользователь **конкретный внешний продукт/artifact** основой, аналогом или parity target.

Триггеры:

- пользователь прислал файл и назвал его референсом;
- дал ссылку на конкретный продукт и просит взять его за основу;
- назвал конкретный продукт/продукты: «как X», «аналог X», «повтори X»;
- обозначил конкретный UI/behavior/preset/render reference.

Тогда MUST применяться [Reference Audit](REFERENCE_AUDIT.md) в заявленном scope **до Technical Design соответствующей области**.

Просто «хочу glow/line generator» или случайное упоминание продукта Reference Audit не включает.

Если непонятно, является ли названный продукт именно референсом, задать один короткий вопрос человеческим языком.

### Новый продукт

Если Product Vision ещё не определён:

**Smart Entry → Stage 0 Product Discovery → Product Vision → Scope → Product Spec → Technical Design → Production Plan → Development.**

### Крупная новая функция / изменение продукта

Если меняются пользовательская ценность, core workflow или product scope — пройти применимый Stage 0 для этой функции.

Если product contract не меняется — перейти к обычному technical planning.

### Bug / regression

Обычно Product Discovery не нужен:

**Reproduction / Evidence → Debugging Protocol → Fix → Regression → Validation при необходимости.**

### Небольшое улучшение

Использовать существующий product contract и выбрать engineering rules по фактическому риску. Не запускать большое интервью, если задача понятна.

### Пользователь хочет попробовать результат

Фразы вроде «дай проверить», «собери мне версию», «хочу попробовать у себя» обычно означают **Validation**, если нет признаков публичного release.

### Пользователь хочет выпустить продукт

Фразы вроде «выпускаем», «выкладываем пользователям», «готовим к продаже» переводят работу в **Release Delivery Gate**.

### Audit-only

Запрос на аудит означает inventory → проверка claims → воспроизведение замечаний → отчёт. Не изменять код или правила, пока исправления не входят в намерение пользователя.

### Research / выбор решения

Для вопросов «можно ли это сделать?», «как лучше реализовать?», «UXP или CEP?» сначала выполнить research / compatibility / technology-maturity analysis. Не начинать implementation до достаточного ответа.

## 4. Когда нужно задавать вопросы

Вопрос нужен только если ответ способен materially изменить:

- продукт или core workflow;
- scope / UX;
- архитектуру;
- compatibility;
- безопасность;
- distribution;
- объём работы;
- acceptance criteria.

Предпочтительно задавать **1–3 связанных вопроса за один заход**, а не большую анкету.

Как только информации достаточно для безопасного следующего этапа, продолжить работу.

## 5. Как задавать вопросы пользователю

Вопрос должен быть на языке цели пользователя.

Плохо:

> Какой Delivery Gate выбрать: Validation или Release?

Хорошо:

> Ты сейчас хочешь просто попробовать эту версию у себя или уже готовим её для публикации пользователям?

Плохо:

> Это Light, Standard или Critical?

Хорошо:

> Эта правка только меняет интерфейс или ещё затрагивает рендер, файлы или сохранение проекта?

Плохо:

> Нужен Stage 0?

Хорошо:

> Полный функционал уже определён или сначала вместе сформулируем, что именно должен делать продукт?

Если нужен технический выбор, ИИ SHOULD сначала исследовать варианты сам, затем спросить пользователя только о продуктовых/UX-компромиссах, которые нельзя решить инженерно.

## 6. Если намерение неоднозначно

Сначала сделать наиболее естественный вывод из контекста.

Уточнять только когда неправильная трактовка может привести к лишней работе, неправильному artifact или изменению product direction.

Типовые вопросы:

- «Ты хочешь пока только проверить версию у себя или уже выпустить её другим пользователям?»
- «Это часть существующего инструмента или отдельный продукт?»
- «Нужно восстановить прежнее поведение или изменить сам принцип работы?»

## 7. Внутреннее решение ИИ

После понимания запроса ИИ самостоятельно определяет:

- triggered ли Reference Audit и какой у него scope;
- нужен ли Stage 0;
- тип artifact / компонентов;
- Risk Profile;
- Delivery Gate;
- применимые Rule Groups;
- необходимые Evidence;
- нужные templates/scripts;
- следующий логичный этап.

Пользователь не обязан утверждать эту классификацию по техническим терминам, если его намерение уже однозначно.

## 8. Загружать только применимые правила

ИИ SHOULD читать минимальный достаточный набор canonical rules для текущей задачи, а не весь repository.

Примеры:

- concrete reference → Smart Entry + Reference Audit + применимые product/engineering rules;
- новый продукт → Smart Entry + Product Discovery;
- bug в JSX → Process Core + Debugging + JSX/Tools;
- validation build → текущие engineering rules + Validation Gate;
- release native plugin → Process/Engineering + Native + Release + применимый platform gate;
- research → только необходимые source/compatibility/technology rules.

Если scope меняется, набор правил пересчитывается.

Это оптимизация чтения, а не ослабление требований: обнаруженный существенный риск нельзя игнорировать только потому, что соответствующий модуль не был выбран сначала.

## 9. Первый ответ после Smart Entry

Если задача понятна — сразу начать работу без формального интервью.

Если есть существенная продуктовая неопределённость — кратко подтвердить цель и задать только несколько ключевых вопросов, не начиная преждевременный Technical Design.

Для существующей понятной задачи достаточно назвать:

1. что будет сделано;
2. существенный риск/ограничение, если он уже виден;
3. первый рабочий этап.

Не заставлять пользователя читать внутренний стандарт перед началом работы.

## 10. Не превращать Smart Entry в бюрократию

Не нужно:

- проходить discovery перед каждым bugfix;
- перечислять пользователю Rule Groups;
- спрашивать разрешение на очевидные обязательные проверки;
- требовать знания инженерных терминов;
- создавать документы без практической пользы.

Если запрос однозначен — классифицировать его внутри и работать.

## 11. Controlled initiative

Если обнаружена критическая architecture/security/data-loss/product-level проблема, применяется [Controlled initiative](WORKFLOW.md):

- кратко сообщить риск;
- предложить альтернативу;
- не менять product direction молча.

## 12. Короткие примеры

**Референс:** «Вот plugin X, сделай аналог» → включить Reference Audit, построить Reference Specification и parity tests до Technical Design.

**Новый продукт:** «Хочу новый AE-плагин» → использовать известный context, при необходимости провести короткий Stage 0, затем перейти к spec/design/plan.

**Bug:** «Export перестал работать» → не спрашивать Product Vision; воспроизвести, применить Debugging Protocol, исправить, проверить regression.

**Проверка:** «Собери версию, хочу попробовать» → трактовать как Validation, если нет признаков публичного release.

## Главное правило

**Пользователь не должен управлять инженерным процессом вместо ИИ.**

Пользователь говорит, чего хочет. ИИ переводит это в применимый процесс AE Development Rules.

## Проверяемые сценарии маршрутизации

[Routing helper](starter-kit/scripts/lib/applicability.mjs) принимает уже определённый context, а не классифицирует свободный текст. [Сценарии](starter-kit/tests/contracts.mjs) проверяют audit-only, bugfix, публичный micro-helper, внутренний milestone и разные reference scopes. Product Discovery и Reference Audit должны быть закрыты до implementation соответствующего scope; helper выбирает требования, но не подтверждает прохождение этапов.

Routing helper возвращает `implementation_task` как тип работы. Это не разрешение начинать реализацию: необходимые Product Discovery / Reference Audit должны быть завершены в соответствующем scope до технического планирования.
