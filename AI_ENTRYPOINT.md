# AI Smart Entry

Этот документ определяет, **как ИИ должен начинать работу по AE Development Rules, когда пользователь описывает задачу обычным языком**.

Пользователь не обязан знать внутренние термины стандарта: Stage 0, Risk Profile, Delivery Gate, Validation Build, Release Gate, Regression Level и другие инженерные категории.

Базовый пользовательский запрос может быть простым:

> Хочу сделать такой плагин. Посмотри правила и начинай.

или:

> Исправь этот баг по нашим правилам.

ИИ обязан сам перевести такой запрос на внутренний язык стандарта.

## 1. Главный принцип

**Пользователь объясняет, чего хочет получить. ИИ самостоятельно определяет, какие правила и этапы для этого применимы.**

Не спрашивать пользователя:

- какой выбрать Risk Profile;
- какой выбрать Delivery Gate;
- нужен ли Stage 0;
- Validation это или Release;
- какой Regression Level нужен;
- какой внутренний checklist использовать,

если это можно определить из контекста и самой задачи.

Внутренние инженерные термины можно использовать в техническом статусе или документации, но не перекладывать выбор этих режимов на пользователя.

## 2. Сначала использовать уже известный контекст

Перед вопросами ИИ SHOULD использовать всё уже доступное и подтверждённое:

- текущую формулировку пользователя;
- предыдущие ответы в разговоре;
- существующий Product Vision / Product Spec;
- repository documentation;
- текущий milestone / issue / checkpoint;
- уже согласованные ограничения и решения.

Не задавать повторно вопрос, ответ на который уже известен.

Если существующий product contract достаточно ясно определяет задачу, не запускать новое интервью только ради формального процесса.

## 3. Внутренняя маршрутизация задачи

ИИ самостоятельно определяет наиболее подходящий путь.

### Новый продукт

Примеры:

- «Хочу сделать новый AE-плагин».
- «Есть идея инструмента для After Effects».
- «Давай сделаем панель, которая...»

Если Product Vision ещё не определён:

**Smart Entry → Stage 0 Product Discovery → Product Vision → Product Scope → Product Spec → Technical Design → Production Plan → Development.**

### Крупная новая функция / изменение продукта

Определить, меняет ли задача:

- основную пользовательскую ценность;
- core workflow;
- product scope;
- существенные UX expectations.

Если да — использовать применимый Stage 0 для этой функции.

Если нет — перейти к обычному планированию изменения.

### Bug / regression

Примеры:

- «Вот ошибка, почини».
- «После обновления это перестало работать».
- «AE падает при таком сценарии».

Обычно новый Product Discovery не нужен.

Путь:

**Reproduction / Evidence → Debugging Protocol → Fix → Regression → Validation при необходимости.**

### Небольшое улучшение

Примеры:

- «Передвинь эту кнопку».
- «Добавь настройку».
- «Сделай это чуть быстрее».

Использовать существующий product contract и определить применимые engineering rules по фактическому риску.

Не запускать большое интервью, если задача уже понятна.

### Пользователь хочет попробовать результат

Примеры:

- «Дай мне проверить».
- «Хочу поставить это себе и посмотреть».
- «Собери версию для моего Mac».

Обычно это **Validation**, а не публичный Release.

ИИ сам применяет Validation Gate и не заставляет пользователя выбирать термин.

### Пользователь хочет выпустить продукт

Примеры:

- «Всё готово, выпускаем».
- «Хочу выложить пользователям».
- «Готовим версию для продажи».
- «Сделай финальный релиз».

ИИ переводит работу в **Release Delivery Gate** и применяет полный применимый Release Gate.

### Исследование / выбор решения

Примеры:

- «Можно ли вообще такое сделать в AE?»
- «Как лучше реализовать эту функцию?»
- «UXP или CEP?»

Сначала выполнить research / compatibility / technology-maturity analysis. Не начинать implementation до достаточного ответа на технический вопрос.

## 4. Когда нужно задавать вопросы

Вопрос задаётся только если ответ способен materially изменить:

- продукт;
- core workflow;
- scope;
- UX;
- архитектуру;
- compatibility;
- безопасность;
- distribution;
- стоимость/объём работы;
- acceptance criteria.

Предпочтительно задавать **1–3 связанных вопроса за один заход**, а не длинную анкету.

Как только информации достаточно для безопасного следующего этапа, интервью следует прекратить и продолжить работу.

## 5. Как задавать вопросы пользователю

Вопрос должен быть на языке цели пользователя.

Плохо:

> Какой Delivery Gate выбрать: Validation или Release?

Хорошо:

> Ты сейчас хочешь просто попробовать эту версию у себя или уже готовим её для публикации пользователям?

Плохо:

> Это Light, Standard или Critical change?

Хорошо:

> Эта функция только меняет интерфейс или она ещё затрагивает сохранение проектов / рендер / файлы?

Плохо:

> Нужен Stage 0?

Хорошо:

> У нас уже окончательно понятно, что должен делать продукт, или ты хочешь сначала вместе определить полный функционал?

Если пользователь не технический, не требовать от него выбрать API, framework, architecture, signing model или runtime без необходимости.

Когда нужен технический выбор, ИИ SHOULD:

1. сам исследовать доступные варианты;
2. кратко объяснить существенную разницу человеческим языком;
3. спросить пользователя только о бизнес-/UX-компромиссе, который нельзя решить инженерно.

## 6. Если намерение неоднозначно

ИИ сначала пытается сделать наиболее естественный вывод из контекста.

Если ошибка маршрутизации может привести к лишней работе или неправильному artifact, задать один короткий уточняющий вопрос.

Типовые примеры:

**Проверка или релиз**

> Ты хочешь пока только проверить эту версию у себя или уже выпустить её другим пользователям?

**Новая функция или новый продукт**

> Это должно стать частью существующего инструмента или мы проектируем отдельный продукт?

**Исправление или изменение поведения**

> Нужно восстановить прежнее поведение или ты хочешь изменить сам принцип работы?

Не раскрывать внутреннюю классификацию как экзамен для пользователя.

## 7. Внутреннее решение ИИ

После понимания запроса ИИ самостоятельно фиксирует для работы:

- применим ли Stage 0;
- тип artifact / компонентов;
- текущий Risk Profile;
- текущий Delivery Gate;
- применимые Rule Groups;
- необходимые Evidence;
- нужные templates/scripts;
- следующий логичный этап.

Эту классификацию можно сохранить в project documentation или кратком инженерном status, но пользователь не обязан её утверждать по терминам, если его намерение уже однозначно.

## 8. Первый ответ после Smart Entry

Для простой и понятной задачи ИИ SHOULD сразу начинать работу без формального интервью.

Для задачи с существенной продуктовой неопределённостью первый ответ обычно содержит:

1. краткое подтверждение понимания цели;
2. несколько самых важных вопросов;
3. без преждевременного Technical Design.

Для существующей понятной задачи первый ответ обычно содержит:

1. что именно будет сделано;
2. существенный риск/ограничение, если оно уже видно;
3. первый рабочий этап.

Не заставлять пользователя читать внутренний стандарт перед началом работы.

## 9. Не превращать Smart Entry в бюрократию

Smart Entry нужен, чтобы **снять сложность с пользователя**, а не добавить новый ceremony.

Не нужно:

- проходить полный questionnaire перед каждым bugfix;
- перечислять пользователю все Rule Groups;
- спрашивать разрешение на очевидную обязательную инженерную проверку;
- требовать знания терминов стандарта;
- создавать документы, которые не помогают принять решение или сохранить product contract.

Если запрос однозначен — классифицировать его внутри и работать.

## 10. Controlled initiative

Если в процессе Smart Entry обнаружена критическая архитектурная, security, data-loss или product-level проблема, применяется [Controlled initiative](WORKFLOW.md):

- кратко сообщить риск;
- предложить альтернативу;
- не менять product direction молча.

## 11. Примеры

### Пример A — новый продукт

Пользователь:

> Хочу плагин, который позволяет складывать несколько слоёв в один контейнер как в Premiere. Посмотри правила и делай.

Правильное поведение ИИ:

- определить, что это новый/крупный product scope;
- проверить существующий context;
- провести короткий Stage 0 interview только по неизвестным ключевым вопросам;
- сформировать Product Vision / Scope;
- только затем проектировать техническое решение.

### Пример B — понятный bug

Пользователь:

> В текущем плагине кнопка Export перестала работать. Почини по правилам.

Правильное поведение ИИ:

- не спрашивать про Product Vision;
- определить существующий artifact/context;
- воспроизвести bug;
- применить Debugging Protocol;
- исправить;
- regression-check;
- сообщить Evidence.

### Пример C — пользовательская проверка

Пользователь:

> Собери мне версию, я хочу попробовать её в AE.

Правильное поведение ИИ:

- самостоятельно трактовать это как Validation, если нет признаков публичного release;
- подготовить идентифицированный Validation Build;
- дать минимальный понятный сценарий проверки.

## Главное правило

**Пользователь не должен управлять инженерным процессом вместо ИИ.**

Пользователь формулирует цель и принимает продуктовые решения.  
ИИ переводит эту цель в применимый инженерный процесс AE Development Rules.
