# Workflow

Операционный порядок работы для проектов, использующих AE Development Rules.

Этот документ описывает **как вести работу и сообщать статус**. Пользовательский вход в процесс определён в [AI_ENTRYPOINT.md](AI_ENTRYPOINT.md). Инженерные требования к тестам, compatibility и Evidence определены в [DEVELOPMENT_RULES.md](DEVELOPMENT_RULES.md).

ИИ SHOULD сначала интерпретировать намерение пользователя через Smart Entry и только затем применять внутренние инженерные режимы. Пользователь не обязан выбирать их вручную.

## 0. До технического планирования

Сначала применить [AI Smart Entry](AI_ENTRYPOINT.md): определить тип запроса, использовать уже известный контекст и решить, нужен ли Stage 0.

Для нового продукта, крупной новой функции или изменения product direction сначала проверить, завершён ли [Stage 0 — Product Discovery](PRODUCT_DISCOVERY.md).

Если Product Vision / core scope ещё не подтверждены, техническое планирование SHOULD не начинаться с архитектуры или списка implementation tasks.

Во время discovery:

- сначала использовать уже известный контекст;
- задавать только вопросы, способные materially изменить продукт;
- не отправлять большую анкету без необходимости;
- отличать Confirmed Requirement / Derived Requirement / Assumption / Open Question / Idea / Non-goal;
- после достаточной ясности собрать Product Vision, Product Scope, Core User Flows и Success Criteria.

После Stage 0 переходить к Product Spec → Technical Design → Production Plan.

## 1. Работа логичными блоками

Разработку вести законченными блоками.

Логичный блок — часть работы, после которой существует проверяемый результат: завершён research, реализована функция, исправлен bug, закончена группа тестов, обновлена документация, подготовлен candidate и т.п.

После каждого законченного блока:

1. сохранить изменения в Git, если работа ведётся в репозитории;
2. выполнить применимые проверки этого блока;
3. кратко сообщить результат;
4. назвать следующий блок.

Не дробить отчёты на каждое мелкое действие и не создавать искусственные этапы ради количества статусов.

## 2. Статус перед значимым этапом

Перед началом значимого этапа инженерно зафиксировать:

- текущий **Risk Profile**: Light / Standard / Critical;
- текущий **Delivery Gate**: Development / Validation / Release;
- текущий этап: `Этап X из Y`, если полный цикл уже определён;
- что уже завершено;
- что делается сейчас;
- следующий ожидаемый результат;
- реальные препятствия или ограничения, если они есть.

Если общее число этапов ещё нельзя определить честно, не придумывать `Y`. Достаточно назвать текущий этап и следующий завершённый результат.

В пользовательском сообщении не нужно автоматически показывать Risk Profile / Delivery Gate и другие внутренние термины. Показывать их только когда это помогает понять риск, статус или решение. Никогда не требовать от пользователя выбрать эти значения самому, если его намерение уже понятно.

## 3. Статус после завершённого блока

Предпочтительный формат:

- **Завершено:** что конкретно сделано.
- **Проверено:** какие проверки реально выполнены.
- **Ограничения:** что осталось непроверенным или заблокированным.
- **Git:** branch / commit / PR, если применимо.
- **Дальше:** один следующий логичный блок.

Статус процесса не заменяет инженерные статусы.

Для результатов проверок использовать только **Test Status** из [core/PROCESS.md](core/PROCESS.md) §10.
Для совместимости — **Compatibility Status**.
Для силы инженерного вывода — **Evidence Confidence**.

## 4. Общение

Общаться:

- коротко;
- человеческим языком;
- без ненужного технического шума;
- с ясным различием фактов, предположений и ограничений.

Технические подробности давать, когда они нужны для решения или понимания риска.

Не говорить «готово», «исправлено», «работает» или «ускорено» без соответствующего Evidence.

Если проверка недоступна, прямо назвать:

- что не проверено;
- почему;
- как это влияет на текущую готовность.

Не изображать выполнение недоступных действий: запуск After Effects, тестирование GPU, проверку другой ОС, установку artifact или подтверждение реально загруженной версии.

## 5. Не перекладывать доступную работу на пользователя

Всё, что разработчик может безопасно проверить сам, должно быть проверено до запроса к пользователю.

Участие пользователя допустимо для:

- проверки уникального окружения;
- UX / визуальной оценки;
- обязательного разрешения доступа;
- предоставления недоступных исходных данных;
- runtime-сценария, который нельзя воспроизвести доступными средствами.

Запрос пользователю должен быть минимальным и проверять один понятный вопрос, а не заменять внутренний QA цепочкой случайных экспериментов.

## 6. Validation Build

Передача Validation Build пользователю не означает release.

Перед пользовательской validation:

- выполнить доступные внутренние проверки;
- идентифицировать artifact;
- дать короткий сценарий проверки;
- явно назвать известные ограничения;
- не требовать полного Release Gate, если он не относится к цели validation.

После ответа пользователя результат фиксируется как Evidence. Пользовательский успех не превращает другие непройденные проверки в PASS.

## 7. Release

Когда работа переходит от validation к финальному release, явно сообщить смену **Delivery Gate: Validation → Release**. Risk Profile при этом не меняется автоматически.

Далее применяется полный **Release Gate** из profiles/RELEASE.md §26 и только те platform-specific gates, которые применимы к фактическому distributable.

## 8. Stop criteria

Не продолжать бесконечный цикл улучшений без нового основания.

Блок можно считать завершённым, когда:

- его критерий приёмки выполнен;
- обязательные проверки этого scope имеют допустимый результат;
- новые изменения больше не нужны для заявленной цели;
- остаточные риски либо устранены, либо явно зафиксированы.

Новый scope оформлять как следующий блок, а не незаметно расширять текущий.

## 9. Controlled initiative

Ассистент / разработчик SHOULD сохранять запрошенный scope и не подменять задачу собственной архитектурной инициативой.

Если во время работы обнаружена существенная проблема вне текущего scope — например риск потери данных, security issue, заведомо хрупкая архитектура, блокирующее ограничение host API или решение, которое сделает заявленный результат недостоверным — её SHOULD кратко сообщить.

Предпочтительный порядок:

1. продолжить запрошенный безопасный scope, если это возможно;
2. отдельно назвать найденный риск;
3. кратко предложить альтернативу и объяснить, что она меняет;
4. не внедрять альтернативную архитектуру молча только потому, что она кажется лучше.

Если исходный путь технически невозможен или небезопасен, это SHOULD быть сказано до существенного изменения архитектуры.

Неблокирующее улучшение MAY быть предложено в конце результата как отдельный следующий scope.

## 10. Представление ручных изменений

Если инструменты позволяют реально редактировать repository, предпочтительно:

- изменять файлы напрямую;
- показывать фактический Git diff / commit;
- не генерировать вручную псевдо-diff, который не соответствует реальному состоянию repository.

Если изменение должен вручную выполнить пользователь, предпочтительный формат:

1. **File:** точный путь.
2. **Find:** точный существующий фрагмент или устойчивые anchors.
3. **Replace:** полный новый фрагмент.
4. **Verify:** короткая команда / проверка результата.

Для маленьких точечных замен формат `Find → Replace` предпочтительнее выдуманных line numbers и вручную написанных diff hunks, которые могут устареть.

Если настоящий Git diff уже получен из repository, его можно использовать как authoritative representation изменения.
