# Workflow

Этот документ задаёт рабочий ритм, не второй набор условий готовности. Обязательное ядро — [Process §1](core/PROCESS.md#1-применение-правил-и-обязательность-проверок); состояние — [Smart Entry §2.2](AI_ENTRYPOINT.md#22-восстановление-и-сохранение-состояния-задачи); передача/релиз — [§26](profiles/RELEASE.md#26-validation-gate-и-release-gate).

## Работа блоками

Выполнять один проверяемый логический блок: цель/приёмка → изменение → затронутые проверки → краткий checkpoint. В нескольких блоках сохранять существующий plan/status; одна малая правка не требует отдельного документа. Новый scope проходит [FEATURE-SET-001](AI_ENTRYPOINT.md#24-новый-набор-функций-в-текущей-разработке), завершение — [TASK-CLOSE-001](core/PROCESS.md#11-критерии-завершения-и-готовности).

## Общение

До значимого действия сообщить, что оно даст; после блока — результат и конкретный открытый пункт/следующий шаг. Не перечислять неизменные правила, не выдавать план за выполненную проверку, не заставлять пользователя выбирать технический профиль. Известный отказ/лимит объяснить по фактической причине. Формат статусов/записей один: [Evidence §10](core/PROCESS.md#10-evidence-и-статусы-проверок).

## 9. Controlled initiative

Повторять попытку только при новой гипотезе/изменённом входе/измеримом прогрессе; при повторе одинакового провала остановить цикл и сохранить причину. Продолжать независимую разрешённую работу. Не расширять scope под видом cleanup, оптимизации или дополнительного релиза. Для материальной смены решения задать вопрос; для обычного разрешённого шага действовать.

## 10. Представление ручных изменений

Дать применимый файл/patch, объяснить куда и зачем его внести и как проверить. Не обещать выполненный runtime пользователя. Для Validation/Release использовать единственный чеклист §26, для уборки — [§6](core/PROCESS.md#6-git-обязателен).
